## 2. 時間配置（公告調整後版本）

每組的硬上限是 **20 分鐘**：

| 段落 | 時間 |
|------|------|
| 簡報 + Demo | 8–12 分鐘 |
| Q&A | 5–8 分鐘 |
| 換場（下一組準備） | 5 分鐘 |
| 響鈴提醒 | 第 8 / 12 / 17 / 20 分鐘各響一次 |

我們本組設定的工作目標是：**簡報 + Demo 約 10 分鐘，Q&A 約 7 分鐘**。
這樣 Demo 萬一卡住還有緩衝時間，也不會撞到 12 分鐘的響鈴。

## 3. 繳交規範

**以組為單位**繳交（一份代表，不是每人一份）：

1. 簡報檔案的 **PDF**。
2. 專案 **Repo 連結（URL）**。

繳交位置：COOL 課程內容，Week 15（6/2）說明。

**截止時間：2026-06-03 00:00。** 繳交完成才算完成期末報告。
未繳交將直接喪失整個期末報告 30% 分數，這不是軟性提醒，而是硬性扣分。

## 4. 評分項度（簡報中必須能看到對應內容）

每一項評分項度都必須出現在簡報裡。每項要「簡單帶過」或「深入說明」由
小組自行安排，但任何一項都不能漏。第二列中明確列出的三張圖是強制要
有的。

| 權重 | 項目 | 簡報需呈現的內容 |
|------|------|------------------|
| 30% | 需求轉換與實作 | User Story、Empathy Map、Acceptance Criteria，可沿用先前作業整合。 |
| 25% | 架構設計與可擴展性 | 具體的架構圖。**必要：** 系統架構圖、Sequence Diagram、ER Model。只有高層次方塊圖不算數。 |
| 25% | 系統測試與驗證 | 測試方式 + 測試結果證明（測試數、覆蓋率、截圖、儀錶板）。 |
| 10% | 程式碼品質 | 如何評估專案程式碼的健全度、可維護性與安全性。評分綜合簡報說明與繳交的 Repo。鼓勵附 SonarScanner / SonarQube 報告。 |
| 10% | 運維與可靠性 | 監控儀錶板，挑了哪些指標、為什麼挑這些指標。 |

## 5. 教學團於預演後給的建議（要對症修正的點）

1. **每一項評分項度都必須出現在簡報上。** 預演時被扣分的組別多半是
   漏掉某一列，或讓那一列只能用「暗示」帶過。簡單帶過 OK，缺席就
   不 OK。
2. **多用圖、少放字。** Icons 與工具截圖比一段段文字有效率得多。
3. **不要直接照搬 AI 產生的簡報。** 套版痕跡明顯的 AI 簡報會被看出
   來，會扣分。要重新整理、優化視覺。
4. **不要照念 AI 文案。** 評審聽得出來。請用自己的話重組，並掌握報
   告的連貫性與故事性。
5. **時間與節奏要練。** 預演表現好的組別大綱完整、節奏流暢、口條清
   晰，約 10 分鐘可完成簡報 + Demo。請把評審當成 **黑客松評審**：
   先放他們想看的，把比重不高的內容適度刪除，不要因為「這部分我們
   花最多時間」就過度聚焦在某一塊。
6. **見樹也要見林。** 不要為了單一子系統的深度，犧牲整體架構的廣
   度。先把廣度鋪滿，再針對最能加分的點補深度。

## 6. 必要圖面檢查清單

下列三張圖都必須出現，建議整頁或近整頁呈現，並配一行說明「為什麼這
樣設計」：

- [ ] **系統架構圖**（Production 上的 AWS 拓樸：ALB、ECS、RDS
      Multi-AZ、S3 圖片儲存、OTLP 出口到 Grafana Cloud）。
- [ ] **Sequence Diagram**（維修申請流程：持有者送出 → 管理員審核
      → 管理員結案，包含 FSM 狀態轉移與 optimistic locking 的
      `version` 檢查）。
- [ ] **ER Model**（`assets`、`users`、`repair_requests`、
      `repair_images`，特別標出 `version` 欄位與外鍵）。
